HighFive

재고 1만 개 쿠폰에 10만 명이 동시에 몰려도 초과 발급 없이 빠르게 처리하는 선착순 쿠폰 발급 시스템

LG U+ 유레카 종합 프로젝트 · 5인 팀 · 백엔드 (저장소 최다 커밋) · github.com/UHO99/HighFive

문제

DB 비관적 락은 정합성은 지키지만 10만 요청에 88.97초, p99 87초가 걸렸고 기본 힙(512MB)에서 OutOfMemoryError까지 났습니다. "원자적으로, 그리고 빠르게" 중 '빠르게'를 못 지켰습니다.

해결

재고 확인과 차감을 Redis Lua Script 하나로 묶어 락 없이 원자성을 보장하고, 결과는 Redis Stream으로 넘겨 DB에 비동기로 쌓은 뒤 배치로 정합성을 검증합니다.

발급 파이프라인

Redis Stream발급 결과
Consumer읽기 전용
WriterJDBC 배치 insert
MySQL발급 이력

담당 업무

영역내용
Lua Script 제안재고 확인과 차감을 따로 보내면 사이에 다른 요청이 끼어들어 별도 락이 필요하고 왕복도 늘어난다고 판단. 하나의 Lua Script로 묶자고 제안해 채택, 발급 파이프라인의 핵심이 됨
DB 적재 병목Consumer가 블로킹 read와 DB 저장을 한 흐름에서 처리해 적재가 밀리던 문제를, 읽기와 쓰기를 분리하고 쓰기는 별도 스레드에서 모아 JDBC 배치 insert로 저장하도록 개선
동기화 배치마감된 쿠폰의 실제 발급 이력 건수와 확정 수량을 맞추는 동기화 배치 구현
검증 배치60초마다 마감 쿠폰을 재대조. 한 번 통과한 쿠폰은 대상에서 제외해 배치 부하가 쌓이지 않게 함
재고 복구Redis 재고 키 유실 시 DB의 유효 발급 건수(취소·만료 제외)로 재고를 재계산해 복구

Proxy Gateway

리버스 프록시·로드밸런싱·오토스케일링·헬스체크의 내부 동작을 Nginx 없이 직접 구현

개인 프로젝트 · 1인 · Go 게이트웨이 + Spring Boot 백엔드 · github.com/UHO99/Simple-Reverse-Proxy-Gateway

문제

처음 만든 게이트웨이는 포트 범위를 고정해 스캔했기 때문에 인스턴스 수가 정적이고, 부하가 늘면 사람이 직접 인스턴스를 늘려야 했습니다.

해결

Docker API로 실행 중인 컨테이너를 찾고, 활성 커넥션으로 부하를 재서 인스턴스를 자동으로 늘리고 줄입니다.

동작 흐름

DiscoveryDocker API
헬스체크goroutine 병렬
라운드 로빈atomic counter
부하 측정ActiveConns
평가임계값·쿨다운
Scalecompose --scale

구현 내용

영역내용
리버스 프록시Gin + httputil.ReverseProxy로 모든 경로를 백엔드로 전달, X-Forwarded 헤더 설정
로드밸런서RWMutex와 atomic counter로 라운드 로빈 선택. 헬스체크는 WaitGroup + goroutine으로 병렬 수행하고 Actuator 상태가 UP인 인스턴스만 풀에 등록
Discovery포트 스캔 대신 compose 서비스 라벨로 실행 중인 컨테이너를 조회. 기존 Backend 객체를 재사용해 갱신 때마다 부하 카운터가 초기화되지 않게 함
오토스케일러Discovery(10초)와 스케일 평가(15초) 주기를 분리. 평균 활성 커넥션이 임계값을 넘으면 1대씩 증감, 쿨다운 적용, 스케일 직후 재discovery 예약

트러블슈팅

증상원인과 해결
Scale In이 전혀 안 됨오토스케일러 초기 인스턴스 수를 실제 조회 없이 최소값으로 고정해, 2대가 떠 있어도 "1대"로 인식. 시작 시 실제 healthy 인스턴스 수로 동기화하도록 수정
compose build 실패build 키에 이미지 태그를 넣은 실수. build(컨텍스트)와 image(태그)를 분리하고, 스케일 시 --no-build로 재빌드 차단
배운 것 - 상태를 들고 있는 로직은 실제 인프라 상태와 애플리케이션이 기억하는 상태가 어긋나는 순간 조용히 멈춥니다. 시작 시점에는 항상 실측값으로 동기화해야 합니다.

Study Room Mate

스터디룸·공간 예약부터 결제까지 처리하는 예약 통합 관리 시스템

LG U+ 유레카 조별 프로젝트 · 3인 팀 · 예약·결제 도메인 (저장소 최다 커밋) · github.com/rmsckd1640/study-room-mate

문제

같은 방·같은 시간에 예약이 동시에 들어오면 중복 예약이 생길 수 있고, 결제를 시작만 하고 끝내지 않은 예약은 자리를 영구히 점유합니다.

해결

예약 시 방을 비관적 쓰기 락으로 잡아 동시 예약을 막고, 결제 상태에 따라 예약 상태를 전환하며, 미완료 예약은 스케줄러가 주기적으로 취소합니다.

담당 업무

영역내용
예약 동시성예약 시 Room을 findByIdForUpdate(PESSIMISTIC_WRITE)로 조회해 동시 요청의 중복 예약 차단, 예약 상태 전환 메서드 설계
결제 연동Toss Payments 위젯 연동과 서버 간 결제 승인, 승인 중 발생 가능한 오류와 successUrl 미전송 처리, 결제에 따른 예약 상태 전환
점유 해제PENDING·READY 상태로 남아 자리를 영구 점유하는 예약을 스케줄러가 10분마다 CANCELED로 변경
구조 개선WebFlux 의존을 RestClient로 교체, 서비스 레이어의 try-catch를 걷어내고 GlobalExceptionHandler로 오류 처리 일원화, 예약·결제 레이어 리팩토링
테스트Repository JUnit 단위 테스트, 관리자 방 생성 → 회원 로그인 → 방 조회 → 예약 시나리오 MVC 테스트, JaCoCo 커버리지
프론트·배포React + Vite 프론트 초기 구조, GitHub Pages 배포 워크플로
